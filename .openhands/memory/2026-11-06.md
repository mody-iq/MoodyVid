# 2026-11-06 — MoodyVid investigation

## Repo shape
iOS "media downloader" for sideloading: Objective-C UI + embedded CPython 3.14
(BeeWare Python-Apple-support `3.14-b14`) + yt-dlp nightly, assembled by
`scripts/assemble.py` into an unsigned IPA via GitHub Actions.

## Verified environment facts
- BeeWare asset is `Python-3.14-iOS-support.b14.tar.gz` (~37 MB); extracts to
  `Python.xcframework/{ios-arm64,lib,build}`. `build/iOS-dylib-Info-template.plist`
  exists (assemble.py fallback never needed).
- iOS has **no ffmpeg**, so yt-dlp cannot merge `bestvideo+bestaudio`.
  Only **pre-merged (muxed)** formats work.
- yt-dlp's *default* YouTube clients return DASH-only (no muxed) for many videos.
  `player_client=android` returns muxed format 18 → required for iOS.
- Format selectors `1080p` / `720p` / `audio` are parsed as **format_id**s, which
  don't exist → "Requested format is not available". This was the main bug.
  Working: `best[height<=720][ext=mp4]/best[height<=720]/best[ext=mp4]/best`.
- yt-dlp uses bundled `certifi` automatically (`dependencies.certifi`), so SSL
  works, but `SSL_CERT_FILE` was only set inside `mvboot.info()`.
- `.fwork` framework shim is a real CPython 3.14 feature
  (`importlib/_bootstrap_external.AppleFrameworkLoader`); assemble.py's naming
  (`x.so` → `x.fwork` + `<module>.framework/<module>` + `.origin`) is correct.
- Missing `NSPhotoLibraryAddUsageDescription` → hard crash on `PHPhotoLibrary`.

## Session 2 — VidGrab-inspired fixes (pushed to main, commit 51e4a81)
Studied github.com/iamjhe08/VidGrab (GPL-3.0) and reimplemented its ideas from
scratch (no code copied) to keep MoodyVid unencumbered.

Shipped:
1. **JavaScriptCore as a yt-dlp JS runtime + challenge provider.** New native
   module `mvnative` in Sources/MVPython.m exposing `run_js(code) -> (ok, out)`
   via JSContext. Registered with `PyImport_AppendInittab` BEFORE
   `Py_PreInitialize` (the order VidGrab uses; calling it after PreInitialize is
   also legal but this order is proven). app/downloader.py registers a
   `JsRuntime` subclass plus an `EJSBaseJCP` provider (`PROVIDER_NAME=
   'javascriptcore'`) at import time.
   WHY IT MATTERS: verified that with NO JS runtime YouTube returns **zero**
   combined video+audio formats; with one, format 18 (360p, combined) appears.
   That is the difference between "download fails" and "download works".
   The provider is picked automatically — no `js_runtimes` param needed.
   Off-device test: stub `mvnative` with node via sys.modules, confirmed
   `[jsc:javascriptcore] Solving JS challenges` and a successful 11.8MB download.
2. **Downloads go to Documents/MoodyVid** via new `MV_DOCUMENTS` env var set in
   MVPython.m; Info.plist gained UIFileSharingEnabled +
   LSSupportsOpeningDocumentsInPlace so the folder shows in the Files app.
   Previously TMPDIR/moodyvid, which iOS purges — that is why audio vanished.
3. **Player-client fallback list** with a 1-hour "last good client" memory,
   replacing the single fixed list that failed wholesale when YouTube blocked it.
4. **Honest labels**: menu is now best available / 720p / 480p / audio (M4A).
   Removed the misleading "1080p" and "MP3".

Still TODO (not started): real progress + cancel (needs a vgnative-style

## Phase 1 UI redesign — tabbed shell (committed, CI green)

New architecture, all under `Sources/`:
- `MVTabBarController` — 4 tabs (Home, Downloads, Files, Settings), SF Symbols only.
- `MVLang` — Arabic + English with a **runtime** switch (`MVLangDidChangeNotification`),
  no `.lproj` bundles (the build only copies `Info.plist` out of `Resources/`).
  Arabic also sets `semanticContentAttribute` to RTL on the root view.
- `MVTheme` — OLED-black dark palette + light palette + Dark/Light/System choice.
  Colours are `colorWithDynamicProvider`; the provider block must resolve against
  the **traits argument**, not `MVTheme.shared.isDark` (wrong on background threads).
- `MVDownloadStore` — JSON-persisted history in `Documents/downloads.json`; records
  left `active` by a crash are shown as cancelled on load.
- `MVPaths` — Documents/cache paths + byte/speed/duration formatters.
- `MVDownloadEngine` — now polls `MVPython` progress at 4 Hz (one NSTimer per task)
  and supports cancel. Engine calls use `download(url, quality, _task="")`.
- `MVPython` — new `progress()/cancelled()` native fns, a `_task` kwarg on `call:`,
  `engineInfo` read from `mvboot.info()` at boot, plus `setProgress:forTask:` etc.
- `app/downloader.py` — `_progress_hook` reports status/progress/speed/eta/total/title
  and **raises `_Cancelled` from the hook** to abort (yt-dlp's documented way).

### Build gotchas found the hard way (ObjC is not compilable locally here)
- `CGRect` is a struct → cannot use the `?:` operator. Use `a ? a.x : b.x`.
- Linking needs **`-framework CoreGraphics -framework QuartzCore`** in
  `scripts/build.sh`; `CGRectZero` and `kCACornerCurveContinuous` come from those,
  and UIKit does not pull them in. Also added AVKit/AVFoundation/CoreMedia for playback.
- `-Wnonnull` warning if an optional param lacks `nullable` under `NS_ASSUME_NONNULL`.
- Workflow: commit → push to `main` → `gh run watch <id>` → `gh run view --log-failed`
  (grep `error:`); each round-trip is ~2 min. There is no local compile, so batch
  the ObjC checks (`python3` brace/paren/bracket balance + missing-header scan).

## User's device test of Phase 1 — three real bugs
1. Language switch did nothing (stayed Arabic). Cause: `MVLang +t:` returned
   `MVTable()[key]` unconditionally; the table holds Arabic only, so every string
   came back Arabic. English wording *is* the key, so it must return `key` when
   the language is not Arabic.
2. No progress bar / speed / ETA and no cancel. Cause: `downloader.py` calls
   `native.set_progress(...)` but only `progress`/`cancelled`/`run_js` were
   registered in `MVMethods`, and the `AttributeError` was swallowed by a bare
   `except BaseException: pass` in the progress hook. Registered `set_progress`.
3. No background downloading. Added a 2-wide queue in `MVDownloadEngine`, one
   `beginBackgroundTask` assertion while work is outstanding, and
   `UIBackgroundModes=fetch`.

Also: 4th tab renamed to **More**, accent changed from violet to **teal #0FA0B0**
to match the user's mockups, and the Home primary button toggles to "Cancel
download" while busy. Note the `busy` ivar must be assigned `_busy = busy;` in the
setter — using `self.busy = busy` recurses and leaves it always NO.

## Traps worth remembering
- `Resources/Info.plist` is **tab-indented**. Any `str_replace` with space
  indentation silently fails to match. Use `\t` in the Python replacements.
- A `&&` chain aborts on the first failure, so a stray `python3 -c "import yaml"`
  (pyyaml is absent) silently skipped the commit *and* the push. Verify with
  `git log --oneline -1 origin/main` rather than trusting the chain's exit code.
- `grep -c '@end'` and similar counts are unreliable here because the injected
  JavaScript string contains `{`/`}`/`[`/`]`. Use `/tmp/check.py`, which is a real
  character scanner that skips string literals and comments.

## Phase 3 — the browser bug the user reported (fixed)
User: "opening YouTube/TikTok from Quick Access does nothing at all."
**Root cause**: in `MVBrowserViewController.buildWebView` the `WKWebView` had
top/leading/trailing constraints but **nothing defined its height**. A `WKWebView`
has no intrinsic content size, so Auto Layout resolved it to zero pixels. The
browser *did* open — with an address bar over a completely empty page, and the
address field was empty too (it is only filled in `didFinishNavigation`). That is
why it looked like nothing happened.
**Fix**: `self.webBottom` constraint, initially to `view.bottomAnchor`, re-pinned
in `buildToolbar` to `row.topAnchor - 8`. Lesson: any view with no intrinsic size
needs both a leading/trailing *and* a top/bottom anchor pair; three anchors is a
silent zero-height layout, not a compile error.

## Phase 4 — matching the reference app's download flow
The user clarified the reference screenshots (ibb IMG-5641..5646) are **their own
downloader app**, not Files: IMG-5646 is the download screen after pasting a
`youtu.be` link — it shows a YouTube page with a **download control**, plus the
video title, channel and date. So the target flow is: paste link -> the app reads
it -> show real metadata + quality choices -> download.

Gap found: our browser offered a **blind** quality list (Best/1080p/720p/480p/MP3)
for every link. Picking 1080p on a 720p video fails, and the user only finds out
afterwards. `MVBrowserViewController` had no metadata step at all.

Changes:
- `app/downloader.py`: new `probe(url)` -> JSON with title/uploader/duration/
  thumbnail/webpage/extractor/heights. `heights` only lists formats where
  `vcodec` and `acodec` are both real, i.e. a **single combined file**, because
  iOS has no ffmpeg to merge. New `_selector(quality)` accepts an arbitrary height
  string ("1080") as well as the named presets; `download()` now uses it.
- `MVBrowserViewController`: `showDownloadSheetFor:title:` presents a "Reading
  link..." alert, calls `probe` via `[[MVPython shared] call:@"downloader"
  function:@"probe" ...]`, then shows the title, channel, duration and only the
  real heights, plus Best/Audio/Cancel. Falls back to the old blind sheet when the
  probe fails, so a broken extractor never blocks downloading.
- The injected page button used to hardcode `'⬇ Download'`; it now contains the
  `__MV_DOWNLOAD__` placeholder that native substitutes from `MVLang`, so the
  button on the page follows the app language.
- `MVLang.m`: added "Reading link...", "Could not read the details; pick a
  quality.", "4K", "1440p".
- `tests/test_downloader.py`: new `DownloadPanelTests` (5 cases). Note: appended
  tests must go **inside a TestCase class** — the file's harness does
  `import downloader` in `setUp`, so module-level test functions raise NameError.
  Suite is now 13 tests + 15 subtests.
