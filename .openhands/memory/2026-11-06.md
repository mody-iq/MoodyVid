## Phase 3 — the browser bug the user reported (fixed)
User: "opening YouTube/TikTok from Quick Access does nothing at all."
**Root cause**: in `MVBrowserViewController.buildWebView` the `WKWebView` had
top/leading/trailing constraints but **nothing defined its height**. A `WKWebView`
has no intrinsic content size, so Auto Layout resolved it to zero pixels. The
browser *did* open — with an address bar over a completely empty page, and the
address field was empty too (it is only filled in `didFinishNavigation`). That is
why it looked like nothing happened.
**Fix**: `self.webBottom` constraint, initially to `view.bottomAnchor`, re-pinned
in `buildToolbar` to `row.topAnchor - 8`. Lesson: any view with no intrinsic size
needs both a leading/trailing *and* a top/bottom anchor pair; three anchors is a
silent zero-height layout, not a compile error.

## Phase 6 — the in-page Download button did nothing (fixed)
Symptom: YouTube opens fine, but tapping the injected "⬇ تنزيل" button does
nothing at all.
**Root cause**: `userContentController:didReceiveScriptMessage:` had this guard
*before* it looked at the message type:
```objc
NSString *src = body[@"src"];
if (![src isKindOfClass:NSString.class] || !src.length) return;   // <-- drops the tap
```
YouTube mobile plays through MSE, so the `<video>`'s `currentSrc` is a `blob:`
URL and is frequently **empty**. The JS posted `{type:'tap', src:''}`, the guard
returned early, and nothing happened — the button looked dead but was firing.
Secondary: the button was `appendChild`-ed into the video's *parent*, where
YouTube's own player overlay sits above it and can swallow the click.

Fixes:
- Only `found` messages need a src. A `tap` now resolves its target with
  `[self looksLikeMedia:src] ? src : self.web.URL.absoluteString`, so an empty or
  `blob:` src falls through to the page URL and the engine extracts it.
- Injected button moved to `document.body` with `position:fixed` (viewport-
  anchored), escaping the page's stacking context. Removed the `sync()` that
  chased the video's offset, since it is no longer positioned relative to it.
- **New native Download button** in the browser toolbar (`arrow.down.circle` →
  `downloadCurrentPage`). Rationale worth remembering: a page can *always* cover
  an element we inject, so an injected-only affordance is never reliable. The
  toolbar button is the guaranteed path; the injected one is a convenience.

Gotcha while editing: patching the injected JS from a Python heredoc is painful
because the strings contain both escaped quotes and literal `\n`. Match on a
substring with **no quotes and no backslashes** (e.g.
`position:absolute;z-index:2147483647;top:12px;right:12px;`) instead of whole
lines, and verify with `repr()` when an assert fails.
Also: an assert failure aborts the script *before* the write, so earlier
`sub()` calls in the same run are silently rolled back — re-check the file after
any AssertionError.

## CRITICAL LESSON (round 7 regression)
- **Never gate the FIRST AVPlayer swap behind a debounce/timer re-check.** My round-7 async `AVURLAsset loadValuesAsynchronouslyForKeys` precheck re-checked `_lastLoadTime` (<0.35s) inside the completion handler. Local files verify in <0.35s, so EVERY first load was dropped → "no downloaded video plays in Files or Downloads". Reverted.
- Correct approach now in `MVPlayerCenter.m`: synchronous cheap guard `canPlayURL:` (extension whitelist + file exists & size>0) then the original proven synchronous `replaceCurrentItemWithPlayerItem` swap. Plus a `watchItem:forIndex:` watchdog (AVPlayerItemFailedToPlayToEndTimeNotification + 3s status==Failed check) that auto-skips undecodable items (AV1/VP9-in-mp4, truncated download), bounded by `consecutiveFailures` counter (reset on user playQueue/playNext/playPrevious). This fixes BOTH freeze and "silently nothing happens".
- Playable extension whitelist: mp4,mov,m4v,mp3,m4a,aac,wav (iOS/AVPlayer). WebM/MKV are excluded from queues and show a share/export alert instead.
