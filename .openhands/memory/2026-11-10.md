## YouTube page-download failure (build 123)

Symptom: tapping the browser download button on a YouTube video opened an empty
"Found media" sheet, and "Download page with yt-dlp" failed with
"the download finished but the file could not be found".

Root causes (reproduced off-device with yt-dlp):
1. The URL handed to yt-dlp was `https://m.youtube.com/?ra=m` (the page the user
   arrived from), not the video. `tab.url` is only set in `didFinishNavigation`,
   but YouTube is a SPA and changes the address via History API without a reload.
   yt-dlp then treats `?ra=m` as the "recommended" tab with **0 items** -> no file.
   Fix: the injected sniffer script reports `location` changes (plus popstate,
   hashchange and a 1.5 s poll); `tab.url` follows the SPA and the page download
   reads `webView.URL` at the moment of the tap.
2. The sheet looked empty because a blob/DASH player exposes no link with a known
   file extension, so the extension-based sniffer found nothing. Fix: a watch /
   shorts / live / embed page is offered as an `MVSniffKindPage` row (routed
   through yt-dlp) and counted in the sniff badge.
3. The error text was misleading. Fix: `_describe_failure` names an empty playlist
   ("not a video") vs a DASH-only video; `_error` strips ANSI and shortens the
   frequent yt-dlp errors (bot block, format missing, 403).

Player clients (tested 2026-11): `android` yields a combined mp4; `ios`/`visionos`
are DASH-only or bot-blocked; `tv_simply`/`web_safari`/`mweb`/`web_embedded` are
bot-blocked. PLAYER_CLIENTS is now `[["android"],["ios"],["visionos"],None]`.

Note: a datacenter IP (this sandbox) is bot-blocked by YouTube, so a real device
on a normal network is the only true test of the download path.

## High quality: on-device merge (build 124, commit 78b80c0)

Goal: 1080p/4K. iOS has no ffmpeg, so yt-dlp cannot join a video stream with an
audio stream. The engine already had a two-step path (`startMergedJob`) but it was
broken and never reached.

Root cause (the real bug): the mux target was `[[videoPath stringByDeletingPathExtension]
stringByAppendingPathExtension:@"mp4"]`, which IS the video fragment. `muxVideo:`
removes its target before exporting, so it deleted its own source -> empty file.
Both fragments also shared one outtmpl, so on a site with no audio-only format
the audio run could overwrite the video file.

Fixes:
- Fragments are named `<title> [<id>].video.<ext>` / `.audio.<ext>` (Python outtmpl).
- `derivedPathFor:suffix:ext:` strips the `.video`/`.audio` marker and appends
  `-merged` (mux) or `-mp3` (encode), so a post-step never writes over its source.
- `isMergedQuality:` now includes `"best"` (was only height >= 1080).
- `+[MVMediaConverter hasAudioTrack:]` lets a merged job finish after the video
  step when the picture already carries sound (a combined-only site) — no second
  download of the same bytes.
- `_fragments` (job id -> paths) + `trackFragment:`/`discardTrackedFragmentsFor:`
  delete fragments on success, failure and cancel.
- `MVMediaConverter` uses each track's own `timeRange.duration` (an asset duration
  can exceed the track), fails on an audio insert error (was ignored), and does
  not add a second audio track to a file that already has one.
- The browser page download now shows the same quality sheet as Home.

Verification: selectors parse via `YoutubeDL.build_format_selector`; tests 17 -> 27;
CI run 42862942282 green (test + build). NOTE: CI macOS runners can be slow to
pick up — run 42862942282's first attempt was cancelled with ZERO steps (no runner
ever assigned); `gh run rerun` then passed. An empty `steps: []` on a cancelled job
means infrastructure, not code.
